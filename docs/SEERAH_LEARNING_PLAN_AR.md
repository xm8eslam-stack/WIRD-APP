# خطة تعلم السيرة النبوية والصحابة — وِرد

**الحالة:** مقترح منتج معتمد الاتجاه، وليس ميزة منفذة بعد  
**الأولوية:** P1 — ثاني أهم محور في المنتج بعد الحفظ والمراجعة  
**تاريخ البحث:** 2026-11-11  
**المالك:** لا تُنشر مادة تاريخية أو حديثية قبل اجتياز بوابة المراجعة العلمية والترخيص.

## 1. الهدف وحدود المنتج

إنشاء مسار تعلّم متدرج وتفاعلي في سيرة النبي محمد ﷺ، ثم سِيَر الصحابة رضي الله عنهم، يساعد المستخدم على الفهم والتذكر والمراجعة، لا مجرد قراءة مقالات طويلة.

هذه ميزة تعليمية أساسية داخل وِرد، لكنها لا تحوّل التطبيق إلى موسوعة أو بوابة إسلامية عامة. يجب أن تظل تجربة القرآن والحفظ هي مركز التطبيق، ويأتي مسار السيرة في المرتبة الثانية مباشرة بعد الحفظ والمراجعة.

### النتيجة التي نريدها للمستخدم
- يعرف أين وصل، وما الدرس التالي، وما الذي أتقنه وما يحتاج إلى مراجعته.
- يتعلم في وحدات قصيرة مترابطة، مع سياق زمني ومكاني وشخصيات مرتبطة بالأحداث.
- يختبر نفسه بعد كل درس، وبعد كل مرحلة، وفي مراجعات تراكمية لاحقة.
- يستطيع متابعة التعلم دون اتصال بعد تنزيل المحتوى المعتمد.
- يرى مصدر كل معلومة، ويعرف بوضوح إن كان التاريخ تقريبيًا أو المسألة مختلفًا فيها.

## 2. قرارات ثابتة قبل التنفيذ

1. **لا نعتمد API واحدًا بوصفه مرجعًا شرعيًا أو تاريخيًا نهائيًا.** واجهة API قناة وصول للبيانات وليست حكمًا على صحتها.
2. **لا توليد آلي للمحتوى الديني.** لا يستخدم الذكاء الاصطناعي لتأليف رواية تاريخية أو حديث أو اقتباس أو نسبة قول إلى النبي ﷺ أو صحابي.
3. كل درس وكل سؤال وكل إجابة صحيحة وكل تاريخ وكل اقتباس يجب أن يرتبط بمراجع محددة قابلة للمراجعة.
4. تمييز الرواية الثابتة عن الضعيفة أو المختلف فيها، وعدم دمج الروايات المختلفة في قصة واحدة مصطنعة.
5. لا نعرض تاريخًا دقيقًا عند عدم ثبوته؛ نستخدم «تقريبًا» أو نطاقًا، ونوضح موضع الخلاف.
6. لا نعرض النبي ﷺ أو الصحابة أو أمهات المؤمنين في صور تجسيدية أو وجوه أو مشاهد تمثيلية. تستخدم خرائط وأماكن ومناظر طبيعية وخطوط وزخارف ورسومًا مجردة.
7. لا نسحب قاعدة بيانات API كاملة بكشط كثيف. نلتزم بحدود الاستخدام، ونطلب إذنًا صريحًا عند الحاجة.
8. لا ننسخ كتابًا أو ترجمة حديثة أو نصًا محميًا لمجرد إمكانية الوصول إليه. يلزم ترخيص واضح للمحتوى وإعادة الاستخدام والتخزين دون اتصال.
9. نبدأ عربيًا، ونصمم نموذج المحتوى لدعم لغات أخرى لاحقًا دون أن نؤخر النسخة العربية.
10. Local-first: المحتوى المنشور والمعتمد يعمل محليًا، ومزامنة تقدم المستخدم لا تجعل قراءة الدرس معتمدة على الاتصال.

### قرار المصادر المقترح
- **المحتوى المنشور:** سجل داخلي محلي/مُصدّر من مستودع المحتوى، بعد مراجعة بشرية موثقة.
- **التحقق التاريخي:** قارن نتائج الدرر السنية عند توفر الوصول، مع المصادر الأصلية المعتمدة ومراجع أهل الاختصاص.
- **الإثراء المنظم:** اختبر SeerahBook وIslamic Network في بيئة تجريبية فقط، ولا تعرض أي نص منهما للمستخدم قبل مراجعة نسبته ومصدره وترخيصه.
- **لا نختار API نهائيًا الآن.** قرار المزود يأتي بعد اختبار عينة ممثلة من أحداث مكة والمدينة والهجرة وبدر وأحد والحديبية وفتح مكة، وعينة من تراجم كبار الصحابة، وقياس التغطية العربية والمصادر والحقوق والاستقرار.

### قائمة تحقق اعتماد أي API
- تغطية النبي ﷺ والصحابة والأحداث والأماكن والعلاقات.
- دقة العربية، التشكيل، الأسماء البديلة، والبحث.
- المصدر لكل معلومة، وإمكانية الوصول إلى الكتاب/الجزء/الصفحة أو رابط ثابت.
- بيان الروايات المختلف فيها وتواريخ الميلاد والوفاة التقريبية.
- ترخيص واضح للاستخدام التجاري/غير التجاري، التخزين المؤقت، إعادة العرض، الترجمة، والتشغيل دون اتصال.
- السعر الفعلي، حدود الطلب، سياسة الإيقاف، ومعدل التوافر.
- سياسة الخصوصية، جمع IP، الاحتفاظ بالسجلات، وموقع المعالجة.
- إمكانية تصدير البيانات وعدم الارتهان لمزود واحد.
- فحص schema، pagination، rate limit، timeout، retries، ونسخ API.
- وجود بديل محلي عند انقطاع المزود.

## 4. تجربة التعلم المقترحة

### أ. خريطة الرحلة
تبدأ الرحلة بخريطة مراحل واضحة، لا قائمة مقالات مبعثرة. التقسيم الأولي المقترح:
1. العرب والجزيرة قبل البعثة والسياق التاريخي اللازم.
2. المولد والنشأة والشباب.
3. بدء الوحي وبدايات الدعوة.
4. الدعوة في مكة والابتلاء والهجرة إلى الحبشة.
5. الإسراء والمعراج وبيعتا العقبة والهجرة إلى المدينة.
6. بناء المجتمع في المدينة.
7. بدر وأحد والخندق وما حولها.
8. الحديبية والرسائل والصلح.
9. فتح مكة وما بعده.
10. حجة الوداع والمرض والوفاة.
11. جيل الصحابة: التعرف على الشخصيات، طبقاتهم، أدوارهم، وصلاتهم بالأحداث.

هذا تقسيم UX مبدئي، لا يقرر وحده صحة ترتيب جزئي أو تاريخ؛ ترتيب كل فصل ومشهد وتاريخه يجب أن يراجعه محرر علمي.

### ب. أشكال التفاعل
- خط زمني يمكن تصفيته بحسب المرحلة والشخص والحدث والمكان.
- خريطة مبسطة للأماكن ذات الإحداثيات المتحققة، مع عدم رسم مسارات أو مواقع غير مؤكدة كحقائق.
- بطاقات الشخصيات: الاسم والكنية والنسب والطبقة والأدوار والأحداث المرتبطة، مع تجنب الجزم بما لا يثبت.
- روابط «من كان حاضرًا؟» و«ما الحدث السابق؟» و«ماذا حدث بعد ذلك؟».
- فصل سردي متصل مقسم إلى مشاهد مترابطة، مع مقدمة سياقية ومصادر ظاهرة.
- «رتب الأحداث» و«صل الشخصية بالحدث» و«حدد المكان» و«من صاحب الموقف؟» عندما تكون الإجابة موثقة.
- بطاقات مراجعة للمعلومات التي نسيها المستخدم.
- وضع قراءة متصلة هو الوضع الأساسي؛ المشاهد تقسيم إيقاعي للنص الموثق لا ذريعة لاختراع حوار أو تفاصيل درامية.
- ملخص نهاية المرحلة وخريطة ما تعلمه المستخدم.

### ج. التحفيز دون إفساد الوقار
- مسار إنجاز، مستويات إتقان، شارات لإكمال وحدات أو مراجعة مرحلة.
- هدف يومي اختياري قصير (مثل درس واحد أو 5 دقائق).
- نقاط تقدم مرتبطة بالتعلم الفعلي لا بمجرد فتح الصفحة.
- لا لوحات صدارة عامة، ولا منافسة على الدين، ولا خصم نقاط أو توبيخ عند الانقطاع.
- لا مؤثرات صوتية طفولية أو احتفالات مبالغ فيها؛ الهوية هادئة ومحترمة.
- لا تصوير للنبي ﷺ أو الصحابة ولا تجسيد لأدوارهم.

## 5. نظام الاختبارات والتثبيت

### أنواع الأسئلة
1. اختيار من متعدد بإجابة واحدة ومشتتات معقولة لا تتضمن معلومات ملفقة.
2. ترتيب أحداث زمنية، مع قبول النطاق الزمني عندما تكون التواريخ تقريبية.
3. مطابقة شخصية بحدث أو دور ثابت.
4. مطابقة مكان بحدث عند ثبوت الموقع.
5. بطاقات سؤال/جواب للاسترجاع النشط.
6. إكمال معلومة قصيرة، فقط عندما تكون الإجابة محددة في مصدر معتمد.
7. اختبار شامل للمرحلة، ثم اختبار تراكمي مختلط من المراحل المكتملة.

### دورة التعلم
- قبل الدرس: سؤال تمهيدي اختياري لقياس المعرفة السابقة.
- بعد كل درس: 3–7 أسئلة مرتبطة حصريًا بمحتوى الدرس.
- بعد المرحلة: اختبار إتقان، مع شرح مختصر للإجابة ومصدرها.
- بعد يوم/عدة أيام: مراجعة الأسئلة التي أخطأ فيها المستخدم، وفق جدولة بسيطة قابلة للتعديل.
- مركز «راجع أخطاءك» يجمع الأسئلة المتعثرة حسب الموضوع والشخص والحدث.
- إعادة المحاولة لا تعاقب المستخدم، وتُحفظ المحاولات بوضوح.

### ضوابط جودة الأسئلة
- لكل سؤال: معرف ثابت، درس/مرحلة، مستوى صعوبة، إجابة صحيحة، تفسير الإجابة، مصدر/مصادر، ومراجع.
- لا سؤال عن معلومة خلافية بصيغة حقيقة قطعية.
- إذا كانت المسألة مختلفًا فيها، يصاغ السؤال عن «ما الذي يذكره المصدر الفلاني؟» أو تستبعد من الاختبار الأساسي.
- لا توليد تلقائي لأسئلة من نص API أو نموذج لغوي في الإنتاج.
- كل سؤال يخضع لمراجعة علمية ولغوية واختبار عدم الالتباس.
- لا تظهر إجابة صحيحة قبل انتهاء السؤال إلا في وضع التعلم المعلن.

## 6. بنية البيانات والمحتوى

### أنواع الكيانات
- `seerahPhase`: مرحلة رئيسية.
- `seerahLesson`: درس مرتب ضمن مرحلة.
- `seerahEvent`: حدث بتاريخ تقريبي/نطاق وتفاصيل المكان.
- `seerahPerson`: النبي ﷺ، الصحابة، والشخصيات التاريخية المرتبطة بالمادة.
- `seerahPlace`: موقع جغرافي مع دقة الإحداثيات ودرجة الثقة.
- `sourceReference`: كتاب/مؤلف/طبعة/جزء/صفحة/رابط/ترخيص.
- `claim`: معلومة ذرية مرتبطة بمصدر وحالة مراجعة.
- `quizQuestion`: سؤال وإجابات ومصدر وتفسير.
- `learningProgress`: تقدم المستخدم في الدروس والمراحل.
- `quizAttempt`: محاولة ونتيجة وأخطاء مرتبطة بنسخة المحتوى.

### حقول أساسية للمعلومة التاريخية
- `claimId`, `entityId`, `statement`, `sourceIds[]`
- `reportStatus`: verified / acceptable_with_note / disputed / weak / rejected / pending_review
- `datePrecision`: exact / approximate / range / unknown
- `reviewerStatus`, `reviewedAt`, `contentVersion`
- `licenseId` وحقوق إعادة العرض/التخزين عند انطباقها.

### تخزين تقدم المستخدم
- حفظ محلي أولًا؛ مزامنة تقدم مختصر UID-scoped عند توفر المزامنة الآمنة.
- لا نضع نصوص الكتب كاملة في Firestore ولا نكرر المحتوى العام داخل حساب كل مستخدم.
- احفظ معرف الدرس ونسخة المحتوى وحالة الإكمال وآخر موضع ومحاولات الاختبار ومؤشرات المراجعة.
- يجب أن تتعامل المزامنة مع تغير نسخة المحتوى، وحذف الحساب، وتعارض جهازين دون فقد تقدم.
- لا تخلط تقدم السيرة مع إحصاءات الحفظ أو ختمة القرآن.

## 7. البنية التقنية المقترحة

1. **Content repository:** ملفات JSON/Markdown منظمة ومتحققة داخل المستودع أو حزمة بيانات مستقلة بإصدارات واضحة؛ النصوص المعتمدة ثابتة ومراجعة.
2. **Provider adapters:** محولات منفصلة لكل API؛ لا تربط واجهة المستخدم بمخطط مزود خارجي مباشرة.
3. **Server-side gateway عند الحاجة:** مفاتيح المزود لا تخرج للمتصفح؛ تحقق من المدخلات والمخطط والحجم والمهلة ومعدل الطلب.
4. **Normalization:** تحويل البيانات إلى نموذج وِرد الموحد مع الاحتفاظ بالمصدر الأصلي ومعرفه وتاريخ جلبه.
5. **Editorial approval:** كل مادة خارجية تدخل حالة pending_review ولا تظهر في المحتوى المنشور قبل اعتمادها.
6. **Caching:** تخزين مؤقت محدود مع TTL وإبطال عند تغيير النسخة؛ لا إعادة استضافة لمحتوى دون حق.
7. **Offline bundle:** تنزيل اختياري لحزم المراحل المعتمدة، مع بيان الحجم والنسخة وإمكانية حذفها.
8. **Learning engine:** ترتيب الدروس، احتساب الإكمال، توليد جلسات اختبار من بنك أسئلة معتمد، ومراجعة الأخطاء.
9. **Progress adapter:** تخزين محلي ومزامنة منفصلة عن بيانات القرآن مع قواعد UID isolation الحالية.
10. **Observability:** قياس أخطاء المزود والمهلة ومعدل التخزين المؤقت دون تسجيل بيانات حساسة أو محتوى مستخدم غير لازم.

## 9. خطة الاختبارات

- Unit: ترتيب المراحل، حالات الدروس، حساب التقدم، احتساب النتائج، اختيار الأسئلة، تكرار المراجعة.
- Content validation: كل درس وسؤال له sourceIds؛ لا مراجع مفقودة؛ لا معرفات مكررة؛ روابط داخلية سليمة؛ كل تاريخ له درجة دقة.
- API contract: schema صالح، timeout، 401/403/429/5xx، HTML بدل JSON، بيانات ناقصة، pagination، تكرار الطلب.
- Security: عدم كشف API keys، التحقق الخادمي، منع الوصول لتقدم مستخدم آخر، حماية HTML والروابط الخارجية.
- Persistence: reload، offline، quota، ترقية نسخة المحتوى، فشل المزامنة، جهازان، تبديل UID.
- UX: RTL، نصوص طويلة، أحجام خط، keyboard، screen reader، reduced motion، 44px touch targets، mobile/tablet/desktop.
- Learning quality: لا غموض في الإجابات، لا تكرار غير مقصود، توزيع صعوبة مناسب، تفسير ومصدر بعد الإجابة.
- Release: CI على exact SHA، فحص تراخيص المحتوى، مراجعة أمنية، تحقق post-merge منفصل عن Production.

## 13. تدقيق أعمق لشروط الاستخدام — تحديث 2026-11-11

### الدرر السنية: شروط مؤثرة على التصميم
صفحة الشروط الرسمية (https://dorar.net/api-services/terms) تضيف قيودًا مهمة يجب اعتبارها جزءًا من قرار التكامل:
- نسبة كل نص بوضوح إلى «الدرر السنية» وإظهار الرابط المرجعي `url` قابلًا للنقر.
- لا يجوز تعديل صياغة الحكم أو اختصاره أو استنتاج حكم غير موجود في الاستجابة؛ وعند عرض الحديث يجب إبقاء خلاصة حكم المحدث المرافقة له.
- لا يسمح بالسحب الجماعي أو إعادة تجميع قاعدة البيانات أو تخزينها كاملة، ولا بإعادة نشر البيانات أو تقديمها كـ API فرعي.
- التخزين المؤقت مسموح لتحسين الأداء فقط لمدة لا تتجاوز 24–48 ساعة، مع تحديث دوري وحذف البيانات المخزنة عند إلغاء الوصول/الخدمة.
- الاستخدام محصور في التطبيق الذي تمت الموافقة عليه، مع خادم وسيط آمن؛ يمنع وضع التوكن في تطبيق العميل.
- الحد المعلن 60 طلبًا في الدقيقة، مع حق المؤسسة في التعديل أو إلغاء المفتاح.
- يجب إتاحة بيئة تجريبية أو وصول للمراجعة قبل النشر.
**الأثر على وِرد:** لا يصلح هذا المصدر وحده لبناء حزمة سيرة offline دائمة أو استيراد corpus محلي كامل. يمكن استخدامه كخدمة تحقق/عرض مباشر محدود بعد الموافقة، مع الإسناد والرابط كما هما. أي محتوى offline يجب أن يأتي من مصدر آخر ذي حقوق تخزين وإعادة عرض واضحة، أو من ملخصات أصلية يكتبها محررون مع الإحالات.

### SeerahBook
- صفحة المطورين تعلن عدم الحاجة إلى مفتاح/تسجيل، وتذكر أن الطلبات محدودة حسب IP وأن الحد اليومي غير مناسب لسحب الرسم البياني كاملًا.
- صفحة API Reference التي تمت معاينتها لم تعرض تفاصيل endpoint كاملة (ظلت في حالة تحميل)، لذلك لا نعتبر schema أو rate limit رقميًا أو شروط إعادة الاستخدام محسومة.
- صفحة المطورين تذكر provenance ومراجع لكل claim، لكن يلزم فحص عينة حقيقية ومطابقة كل مرجع، وطلب توضيح مكتوب بشأن الترخيص وإعادة العرض والتخزين المؤقت/offline والاستخدام التجاري قبل نشر البيانات.
**الأثر على وِرد:** يصلح مبدئيًا لاستكشاف محدود read-only فقط، وليس مصدرًا لتعبئة قاعدة وِرد أو إنشاء offline bundle قبل حسم الحقوق.

### Islamic Network
- صفحة APIs تصف People وEvents كـ Early Access وتعلن أن الخدمات مجانية ومفتوحة وتطلب cache responses.
- شروط الاستخدام العامة تنص على إتاحة الخدمات «كما هي» دون ضمان، لكنها لا تقدم في الصفحة التي تمت مراجعتها ترخيصًا تفصيليًا لحقوق نصوص People/Events أو إعادة نشرها أو تخزينها أو ترجمتها.
**الأثر على وِرد:** لا نستنتج من «free/open» وحدها حق إعادة النشر أو التخزين دون اتصال. يلزم تحديد الترخيص الفعلي لمجموعة البيانات والحصول على توضيح قبل إدخالها في corpus.

### قرار محدث
- **Dorar:** مرشح عرض/تحقق مباشر محدود فقط بعد الموافقة، مع قيود cache والإسناد والرابط وعدم التخزين الجماعي.
- **SeerahBook:** مرشح تجربة API محدودة، بانتظار توثيق schema والحقوق والخصوصية والحدود.
- **Islamic Network:** مرشح POC فقط، بانتظار ترخيص واضح وتغطية موثقة واستقرار الخدمة.
- **لا يوجد مصدر API صالح حاليًا لاعتماد corpus كامل أو offline bundle** بناءً على الأدلة العامة التي تمت مراجعتها.


## 14. مراجعة مواصفات API الفعلية — تحديث 2026-11-11

تم فتح صفحات المطورين ومواصفات OpenAPI المنشورة، وليس الاكتفاء بوصف صفحة التسويق.

### Islamic Network — ما اتضح من OpenAPI

**People API**
- مواصفة OpenAPI تعرّف `GET /people` بقائمة صفحات، و`GET /people/{slug}` كسجل شخص موسع.
- سجل الشخص يتضمن اسمًا متعدد اللغات بمفاتيح BCP 47، وhonorific/epithet، ونوع الشخصية، ومكانًا، وسنة ميلاد/وفاة عند توفرها، وسيرة نصية متعددة اللغات، وروابط مجمعة إلى أحداث واقتباسات وقصص وعلاقات.
- مواصفة الـ schema توضح أن النص متعدد اللغات، وأن الحقول الفارغة تُحذف؛ لذلك لا يجوز افتراض أن العربية موجودة لكل سجل.
- نوع الشخصية يتضمن companion، لكن السجل نفسه ليس شهادة توثيق أو تخريج لكل دعوى. يلزم مصدر لكل claim ومراجعة مستقلة قبل استخدامه في درس أو اختبار.

**Events API**
- المواصفة تصف `GET /events` و`GET /events/{slug}` و`GET /calendar/{month}` و`GET /calendar/{month}/{day}` و`GET /calendar/today`، مع ترقيم صفحات وروابط إلى سجل الأشخاص.
- نقطة مهمة: تاريخ `date` في الحدث هو **ذكرى سنوية هجرية** (الشهر واليوم)، بينما `year` اختياري ويعبر عن سنة وقوع الحدث. لا يجوز استخدام تاريخ الذكرى كأنه تاريخ تاريخي مثبت للحدث.
- وصف الـ API يقول إن قائمة الأحداث مرتبة تقويميًا، ونتائجها قد تتضمن مناسبات/مواليد/وفيات وأحداثًا تاريخية. لذلك لا تصلح وحدها كمنهج كامل متسلسل للسيرة، ولا تغني عن قاعدة أحداث محررة ذات علاقات وتسلسل ومراجع.
- مواصفات People/Events منشورة بصيغة OpenAPI JSON/YAML، ما يسمح ببناء contract tests ومحولات typed إذا اجتاز المصدر بوابة الاعتماد.

**الحقوق والتوافر**
- صفحة APIs تصف الخدمة بأنها مجانية ومفتوحة ودون مفتاح، وتطلب التخزين المؤقت؛ وصف People وEvents لا يزال Early Access.
- صفحة الشروط العامة تنص على أن الخدمات تقدم دون ضمان. ويوجد رد من ممثل الخدمة في المنتدى يوضح أن خدمات APIs والمحتوى متاحة للاستخدام مجانًا، وأن شروط كل خدمة تسري، وأن حدود المعدل منشورة؛ لكن هذا الرد لا يقدم ترخيصًا تفصيليًا منفصلًا لمحتوى People/Events أو يحدد حقوق النسخ الدائم والترجمة والحزم offline.
- النتيجة: يمكن إدراج Islamic Network ضمن POC مجاني منخفض المخاطر من ناحية تكلفة الطلب، لكن لا نعتمد تخزين corpus أو إعادة نشر biographies/stories/quotes/offline قبل تأكيد حقوق المحتوى كتابةً. افصل ترخيص كود العميل عن حقوق البيانات والنصوص.

### SeerahBook — ما اتضح من صفحات المطورين وAbout
- REST API للقراءة فقط، دون مفتاح/تسجيل بحسب صفحة المطورين، وتشمل People/Events/Tribes/Places/Sayings & Actions/Sources/Search، مع `include=` لجلب العلاقات المرتبطة.
- الطلبات محدودة حسب IP، والصفحة تحذر من أن الحد اليومي ليس مناسبًا لسحب الرسم البياني بالكامل.
- صفحة About تقول إن المحتوى مبني على سلسلة محاضرات للشيخ ياسر قاضي وتفريغها، وأن كل claim مرتبط بالمحاضرة والمصادر الكلاسيكية التي تستند إليها. كما توضح علامات التاريخ التقريبي والخلاف وضعف السند واختلاف التفاصيل.
- تحذير تحرير مهم: الصفحة تميز بين النص المنقول حرفيًا والصياغة الدرامية/إعادة البناء المحتملة. وصرحت أن كلام النبي ﷺ لا يُدرج بصياغة درامية. لذلك لا نقتبس أي wording أو sayings/actions من المصدر كلفظ حرفي إلا إذا أمكن فتح المصدر الأصلي والتحقق من اللفظ. لا نحول السرد المعاد بناؤه إلى اقتباس أو حوار.
- صفحة API Reference كانت تعرض "Loading API docs" في المعاينة، لذلك تفاصيل schema الكاملة، pagination، والحدود الرقمية لم تُثبت في هذه المراجعة. نحتاج اختبار contract فعلي محدود ومراجعة شروط الاستخدام والخصوصية.
- النتيجة: مرشح ممتاز كفهرس/خريطة استكشاف للمراجع والعلاقات، لكنه ليس مصدرًا وحيدًا للمحتوى المنشور أو نصوص الاقتباس أو حزمة offline حتى تتضح الحقوق.

### معمارية المصادر المقترحة بعد هذه المراجعة
1. لا يوجد "API وحيد للسيرة كاملة". ابنِ **WIRD Seerah Content Registry** كمرجع داخلي، وكل سجل فيه claim IDs ومصادره وحالة مراجعته وحقوقه.
2. استخدم SeerahBook لاكتشاف الكيانات والعلاقات والمراجع المحتملة، وIslamic Network People لتجربة بنية التراجم، وEvents لاقتراح مناسبات تقويمية فقط، والدرر للبحث/التحقق عند الموافقة.
3. اكتب دروس وِرد كملخصات تعليمية أصلية من محررين، لا نسخًا من API أو كتب. كل فقرة لها claims موثقة وروابط للمراجع.
4. بنك الأسئلة مشتق يدويًا من claims معتمدة؛ لا تستخرج أسئلة مباشرة من API ولا تجعل LLM ينشئ إجابات منشورة.
5. لا تفعّل تنزيلًا offline لمحتوى مزود إلا إذا كانت حقوق التخزين وإعادة العرض offline واضحة ومكتوبة. يمكن تخزين محتوى WIRD الأصلي الذي يملك وِرد حقوقه.
6. في المرحلة الأولى، يمكن تجربة API live للبحث والاستكشاف خلف محول خادمي أو أداة تطوير فقط، دون إرسال نصوص خام للمستخدم النهائي ودون تخزين طويل الأجل.

### اختبار POC محدود — تعريف قبل التنفيذ
- عينة 10–15 سجلًا فقط، لا crawl ولا pagination شاملة.
- شخصيات متنوعة: أبو بكر، عمر، عثمان، علي، خديجة، عائشة، بلال، سلمان، مصعب، خالد (إذا كانت متاحة).
- أحداث: بداية الوحي، الهجرة، بدر، أحد، الخندق، الحديبية، فتح مكة.
- قياس: وجود العربية فعليًا، مصدر كل فقرة، اتساق slug والعلاقات، دقة التاريخ/التقويم، نقص الحقول، استقرار endpoint، rate limit، وحق العرض/النسخ/cache/offline.
- احفظ نتائج الـ POC في ملف منفصل ولا تضع البيانات الخام في مستودع التطبيق قبل الموافقة.
- لا تستخدم أسماء الشخصيات في اختبارات تنشئ حقائق أو أسئلة؛ الاختبار هنا على schema وجودة provenance فقط.


## 15. تدقيق provenance على مستوى الحقول — قرار اعتماد أدق

بعد قراءة مخططات `PersonDetail` و`EventDetail` نفسها، هناك فجوة يجب عدم تجاوزها:

- `PersonDetail.biography` حقل نصي متعدد اللغات، لكن المخطط لا يعرّف معه قائمة مصادر لكل فقرة أو claim. كذلك birth/death وhonorific/epithet لا تحمل في المخطط إحالة مستقلة لكل قيمة.
- روابط الشخص إلى events/quotes/stories والعلاقات مفيدة للتنقل، لكنها لا تثبت مصدر كل معلومة في السيرة الذاتية. حقل `source` في EventDetail عبارة عن نص مصدر عام، وليس بالضرورة مرجعًا ببليوغرافيًا قابلًا للتدقيق.
- `QuoteRef` يعرّف `source` كنص و`url` للرواية/الاقتباس، لكنه لا يضمن وحده بيانات الكتاب/الطبعة/الجزء/الصفحة أو حكم صحة الإسناد.
- لذلك لا يجوز تحويل biography أو dates أو relationships من Islamic Network مباشرة إلى claims منشورة أو أسئلة. يمكن استخدام الـ API كفهرس اكتشاف/مرجع تنقل، ثم إعادة بناء كل claim من مصدر أصلي/علمي قابل للفحص.
- يجب أن يحتوي سجل WIRD الداخلي على مصدر مستقل لكل معلومة: اسم الكتاب/المؤلف/الطبعة/الجزء/الصفحة أو رابط موثوق ثابت، النص الأصلي عند الحاجة، ملاحظة اختلاف الروايات، اسم المراجع وتاريخ المراجعة.
- **بوابة اعتماد Islamic Network People:** لا يُعتمد مصدرًا أساسيًا لمحتوى السيرة ما لم يقدم الفريق مصدرًا claim-level أو توثيقًا إضافيًا مكتوبًا يتيح التحقق من كل biography/date/relationship. وإلا يبقى فهرسًا مساعدًا فقط.
- **بوابة اعتماد Islamic Network Events:** حقل source النصي لا يكفي وحده؛ يلزم فتح المرجع الأصلي والتحقق من الحدث والتاريخ. وdate الشهر/اليوم هو ذكرى سنوية لا تاريخ وقوع.
- **بوابة اعتماد SeerahBook:** وجود source provenance لكل claim كما يصف الموقع ميزة مهمة، لكن يجب فتح المصدر الأصلي والتحقق من النص، وعدم اعتبار المحاضرة وحدها بديلًا عن المصدر الكلاسيكي، وعدم استخدام أي صياغة درامية كاقتباس حرفي.
- **النتيجة الحالية:** لا يوجد API من المرشحين الثلاثة يثبت وحده كل متطلبات corpus التعليمي الموثق offline. بناء سجل محتوى وِرد مستقل ليس خيارًا احتياطيًا؛ بل هو التصميم الأساسي.


## 16. قرار تجربة المنتج: «حكاية السيرة» — كتاب تاريخي تفاعلي لا سلسلة دروس

**هذا قرار منتج أساسي، ويعلو على أي صياغة سابقة قد توحي بأن الميزة مجرد قائمة دروس قصيرة.** التجربة المقصودة رحلة قراءة متصلة تشبه كتاب سيرة محققًا ومقسمًا إلى أجزاء وفصول ومشاهد، مع أدوات تعلم مدمجة داخل الحكاية. القراءة والسرد هما قلب التجربة؛ الاختبارات والبطاقات أدوات مساندة.

### 16.1 الوعد التحريري وتجربة القارئ
- يدخل القارئ إلى الرحلة ويرى مقدمة وفهرس الأجزاء ونسبة تقدمه وآخر موضع توقف عنده والفصل التالي المقترح.
- يتكون العمل من أجزاء كبرى، وكل جزء من فصول مترابطة، وكل فصل من مشاهد سردية متتابعة. المشهد وحدة قراءة قصيرة نسبيًا، لكنه لا يختزل الحدث أو يقطع سياقه لمجرد فرض طول ثابت.
- يفتتح الجزء بمقدمة سياقية تشرح الزمان والمكان والأشخاص وأهمية المرحلة. ثم تمضي الفصول بترتيب زمني/موضوعي محرر، وتنتهي بخاتمة تربط آثار المرحلة بما يليها.
- يبدأ الفصل بتمهيد جذاب غير مضلل، ثم سرد متماسك، ثم وقفة فهم اختيارية، وينتهي بملخص وروابط للشخصيات والأماكن والأحداث ومراجعه.
- نهاية كل فصل تجيب: ماذا حدث؟ لماذا كان مهمًا؟ وما الذي يقودنا إلى الفصل التالي؟ مع تشويق أمين لا يصطنع أحداثًا أو يحجب حقيقة لازمة.
- القراءة المتصلة مثل الكتاب متاحة دائمًا، ويمكن فتح الفهرس أو الشخصيات أو الخط الزمني أو الخريطة دون فقدان موضع القراءة.

### 16.2 هيكل العمل المقترح
1. العالم الذي سبق البعثة: الجزيرة العربية ومكة والسياق التاريخي الذي تثبته المصادر.
2. النشأة وبدايات الرسالة: المولد والنسب والطفولة والشباب وبدء الوحي، مع بيان اختلاف الروايات والتواريخ.
3. الدعوة في مكة: الدعوة الأولى والاستجابة والمعارضة والابتلاء والهجرة إلى الحبشة.
4. من مكة إلى المدينة: الأحداث السابقة للهجرة وبيعتا العقبة والهجرة واستقبال المدينة.
5. بناء المجتمع الجديد: المجتمع والمسجد والمؤاخاة والعلاقات والعهود.
6. سنوات التحول والمواجهة: بدر وأحد والخندق وما يتصل بها من سياق ونتائج.
7. الصلح واتساع الدعوة: الحديبية وما تلاها والرسائل والوقائع المرتبطة بها.
8. فتح مكة وما بعده: الفتح والوفود والأحداث اللاحقة حتى حجة الوداع.
9. ختام النبوة وأثر الرسالة: حجة الوداع والمرض والوفاة وما ثبت من الأحداث.
10. الجيل الذي حمل الأمانة: سير الصحابة في ملفات مترابطة زمنيًا وموضوعيًا، لا تراجم معزولة.
11. عصر الخلفاء الراشدين: مسار تاريخي مستقل متصل زمنيًا، مع توثيق الخلافات وعدم تبسيطها إلى رواية أحادية.

هذا فهرس تأسيسي قابل للتحرير العلمي، وليس حكمًا نهائيًا على التقسيم أو التواريخ. لا ينشر فصل قبل اعتماد تسلسله ومراجعه.

### 16.3 قواعد كتابة السرد
- سرد عربي فصيح سهل، حي وواضح، بإيقاع متنوع وفقرات مترابطة؛ لا لغة مدرسية جافة ولا مبالغة روائية.
- شرح الأسماء والقبائل والمصطلحات والأماكن عند أول ظهور، مع إحالات داخلية.
- عرض الخلفية التاريخية بالقدر الذي يخدم فهم الحدث، لا حشو موسوعي.
- لا راوٍ يصف مشاعر أو نوايا لم تثبت، ولا حوار متخيل، ولا تفاصيل حسية أو مكانية بلا أصل.
- لا تنسب عبارة مقتبسة لشخصية إلا إذا ثبت لفظها في مصدر محدد؛ وإلا تستخدم صياغة غير مباشرة واضحة.
- لا تدمج روايتين متعارضتين في مشهد واحد. تعرض الروايات في مساحة «اختلاف الروايات» مع بيان درجة الثبوت وسبب عدم الجزم.
- لا cliffhanger مصطنع ولا تأخير لمعلومة لازمة. التشويق يأتي من تسلسل الوقائع الثابتة ونتائجها.
- يراجع المحرر العلمي السرد ككل؛ فقد تكون الجمل منفردة صحيحة بينما يؤدي ترتيبها أو ربطها إلى معنى مضلل.

### 16.4 وحدات التفاعل المدمجة داخل الكتاب
- على خط الزمن: تاريخ أو نطاق زمني ودرجة دقته.
- على الخريطة: مكان موثق مع بيان دقة الإحداثيات.
- تعرّف إلى الشخصية: بطاقة مختصرة وروابط ظهورها في الفصول الأخرى.
- مصطلح أو سياق: شرح قابل للطي دون قطع القراءة.
- توقف واسأل نفسك: سؤال فهم أو توقع لا يكشف الإجابة قبل الاختيار.
- بعد المشهد: سؤال أو اثنان عند ملاءمة السياق، ويمكن تخطيهما.
- نهاية الفصل: ملخص مترابط وأسئلة استرجاع ومراجعة أخطاء اختيارية.
- نهاية الجزء: اختبار تراكمي وخريطة مفاهيم وشخصيات وأحداث وروابط للفصول التي تحتاج مراجعة.
- كل سؤال وإجابة وتفسير مشتق يدويًا من claims معتمدة، وله مراجع ونسخة محتوى؛ لا توليد تلقائي منشور.

### 16.5 واجهة القراءة
- واجهة قارئ كتاب أولًا: عنوان الجزء والفصل، مؤشر تقدم هادئ، محتوى عربي مريح، مصادر واضحة، تنقل سابق/التالي، وفهرس جانبي أو منبثق.
- وضع «قراءة متصلة» يزيل المقاطعات الاختبارية؛ ووضع «قراءة وتعلّم» يظهر نقاط التفاعل الاختيارية.
- حفظ آخر فصل ومشهد وموضع قراءة محليًا أولًا، ثم مزامنة تقدم صغيرة مستقلة.
- علامات مرجعية وملاحظات شخصية محلية اختيارية، وإعدادات الخط والتباعد والعرض الليلي.
- تصميم متجاوب ودعم قارئ الشاشة ولوحة المفاتيح، دون إجبار القارئ على فتح بطاقة أو اختبار بعد كل فقرة.

### 16.6 معيار قبول تحريري وتجريبي
لا يعد الـMVP مقبولًا إذا كان مجرد cards أو قائمة دروس واختبارات. يجب أن يثبت نموذجًا لجزء افتتاحي له مقدمة وفهرس، وفصلًا مكتوبًا كسرد متصل متعدد المشاهد مع إحالات claim-level، وقارئًا يحفظ موضع القراءة، وانتقالات بين الفصول، وبطاقات سياقية غير مشتتة، واختبارًا اختياريًا بعد الفصل، وبيان الروايات والتواريخ التقريبية داخل سياق القراءة، ومراجعة علمية ولغوية وتجربة قارئ.

**القرار التنفيذي:** أعد تصميم S1 وS2 حول كتاب تفاعلي متسلسل؛ لا تبدأ ببناء محرك الاختبارات أو تكامل API باعتبارهما المنتج. ابدأ بتجربة تحريرية/UX صغيرة ومراجعة مصادرها، ثم ابنِ محرك القراءة والتقدم، ثم أدوات التفاعل والاختبار.
